## Skipped schedule root cause and repair
- Recorded hourly run `43147244569` (12 Nov): `test=success`, `browser-qa=skipped` by design, `project=success` (WIF and source validations), **`deploy=skipped`**. The workflow still concluded success, but **no new Pages deployment occurred on that scheduled run**.
- GitHub Actions' implicit `success()` condition propagated the intentionally skipped `browser-qa` ancestor to the `deploy` job. Source validation had its own `always()` exemption, but `deploy` did not.
- Revised deploy expression: `!cancelled() && needs.project.result == 'success' && (github.event_name != 'workflow_dispatch' || inputs.publish)`. This explicitly accepts a completed successful source-build regardless of the skipped optional browser QA, but rejects failed, skipped or cancelled mandatory builds. Manual publish switch remains respected.
- Added `scheduled-refresh-assert`: on schedule, mark the run **failed** unless both `project` and `deploy` actually succeed. This prevents misleading green scheduled workflow results.
- New Python schedule-regression tests; existing public artifact QA, Chromium desktop/mobile QA and live authenticated data publisher unchanged. Standard source build and served-page release verification required before tagging `v1.7.1`.
